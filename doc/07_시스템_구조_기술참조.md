## DB 스키마 (news_articles)

```sql
CREATE TABLE news_articles (
    id            SERIAL PRIMARY KEY,
    title         TEXT NOT NULL,
    link          TEXT UNIQUE,           -- 중복 방지 기준
    source        TEXT,                  -- 뉴스 소스명
    published     TEXT,                  -- 발행 날짜 (문자열)
    collected_at  TIMESTAMP WITH TIME ZONE DEFAULT NOW(),  -- UTC 저장
    content       TEXT,                  -- 기사 본문 (요약)
    quality_score FLOAT,                 -- AI 품질 점수 (0~1)
    is_selected   BOOLEAN DEFAULT FALSE, -- 선별 여부
    is_analyzed   BOOLEAN DEFAULT FALSE, -- AI 분析 완료 여부
    analysis_result TEXT,                -- AI 분析 결과 (JSON)
    ai_model      TEXT,                  -- 분析에 사용한 AI 모델
    extracted_keywords TEXT,             -- 추출된 키워드 목록
    unit_id       TEXT,                  -- 귀속 단(팀) ID
    embedding     VECTOR(1536)           -- OpenAI 임베딩 벡터 (RAG용)
);
```

자동 마이그레이션: `check_and_migrate_database()`가 시작 시 스키마를 확인하고  
누락 컬럼을 자동으로 추가합니다.

## 데이터 흐름 상세

> 아래는 실제 운영에 사용하는 `run_all_units_daily_optimized()` 최적화 파이프라인을 기준으로 합니다.

### Phase 1: 통합 수집 (`get_news_data()`)

```
① Google Alerts RSS 파싱 (feedparser)
   └── 각 RSS URL에서 entry 목록 수집

② 네이버 뉴스 API 호출
   └── naver_queries의 각 키워드로 검색 API 호출

③ 표준화 기관 RSS 파싱
   └── ITU, ISO, 3GPP 등 공식 기관 RSS

④ 3단계 조기 ICT 필터 (수집 단계)
   ├── L2: 강한 ICT 마커 → 즉시 통과
   ├── L3: 비ICT 패턴 (ETF/채권/전쟁/부동산 등) → 즉시 제외
   └── L4: AI 컨텍스트 마커 → 통과

⑤ URL 기반 중복 제거
```

### Phase 2: 룰 기반 단별 분류 (`_classify_article_to_units()`)

```
① 각 기사 제목을 단별 키워드 집합과 매칭
② 매칭 점수 계산 → 최고 점수 단을 primary_unit으로 배정
③ 모든 매칭 단에 기사를 unit_pools에 추가 (1기사 다단 배정 가능)
④ 수집 기사 전체를 DB에 저장 (save_news_to_db)
```

### Phase 2.5: 타이틀 유사도 클러스터링 (`_dedup_pool_by_title()`) ★ v5.2 추가

```
동일 사건을 여러 언론사가 보도한 기사를 병합 (분析 전 API 비용 절감)

• threshold_numeric = 0.35  — 같은 제품·버전 번호를 공유하는 기사
• threshold_text   = 0.50  — 번호가 다른 경우의 제목 키워드 유사도

예) "갤럭시 A37 5G 출시" 기사 8건 → 대표 1건만 이후 단계로 전달
```

### Phase 3: Unique 기사 병렬 심층 분析 (`analyze_news_with_ai()`)

```
① 단별 풀에서 URL 중복 제거 후 unique_candidates 생성 (최대 50건/단)
② ThreadPoolExecutor(5개 워커)로 병렬 처리
   ├── 기사 본문 추출 (get_article_content)
   └── AI 분析 (GPT-4o 또는 Claude):
       ├── 200자 이내 요약
       ├── 핵심 키워드 5개 (구조화 JSON)
       ├── 표준화 시사점
       └── 중요도 등급 (HIGH/MEDIUM/LOW)
③ 결과를 DB analysis_result(JSON)로 저장
④ extracted_keywords로 단 배정 재검토 (reclassify_article_unit)
```

### Phase 3.5: 타 단 컴팩트 브리프 생성

```
각 단의 분析 기사 목록을 요약 브리프로 압축
→ Phase 4 이메일의 '타 단 동향' 섹션에 삽입
```

### Phase 3.6: 키워드 기반 의미적 중복 클러스터링 (`_dedup_analyzed_by_keywords()`) ★ v5.2 추가

```
Phase 2.5에서 제거하지 못한 '의미는 같지만 표현이 다른' 기사를 제거

• AI 분析이 생성한 extracted_keywords(JSON)의 term 집합을 비교
• Jaccard 유사도 ≥ 0.30 이면 같은 주제로 판정 → 앞 기사 1건만 유지

예) "한일 6G 전파정책 협력" 10건
    → extracted_keywords에 {6G, 위성통신, 전파, 한일, 과기정통부} 공통 포함
    → 0.30 임계값 충족 → 대표 1~2건으로 축소
```

### Phase 4: 단별 리포트/이메일 발송

```
① 각 단의 분析 기사(최대 20건) 기반으로 HTML 이메일 생성
   ├── 이메일 상단: 팩트 전용 일일 브리프 (핵심 이슈 요약)
   ├── 단별 분析 기사 목록
   └── 타 단 동향 섹션 (Phase 3.5 브리프)
② Gmail SMTP로 발송
③ Google Drive에 주간 누적 엑셀 저장
   └── BytesIO 버퍼로 기존 파일 다운로드 → 누적 후 재업로드
       (GitHub Actions 클린 환경에서도 주간 누적 유지됨)
④ 주말(토·일)은 이메일 발송 건너뜀, 분析 결과는 DB에 저장
```

## auto_intel_report.py 파이프라인 상태 기계

`auto_intel_report.py`는 7개 노드로 구성된 파이프라인입니다.

```
node_load_data
    │
    ▼
node_detect_surges ─── 급등 없으면 ─▶ node_build_report ──▶ node_send_report
    │
    ▼ (급등 감지 시)
node_rag_retrieve
    │
    ▼
node_gen_narrative
    │
    ▼
node_build_report
    │
    ▼
node_append_to_doc
    │
    ▼
node_send_report (skip_email=True이면 건너뜀)
```

각 노드 오류는 `state['errors']`에 누적되며,  
치명적 오류 발생 시 후속 노드가 중단됩니다.

## RAG 검색 구조 (rag_search.py)

```
사용자 질문
    │
    ▼
OpenAI text-embedding-3-small으로 질문 벡터화 (1536차원)
    │
    ▼
Supabase에서 코사인 유사도 상위 기사 검색
    │
    ▼
키워드 매칭 검색 결과와 결합 (하이브리드)
    │
    ▼
관련 기사 컨텍스트로 GPT-4o 답변 생성
    │
    ▼
답변 + 참조 기사 목록 반환
```

### 중복 제거 임계값 (config.json 또는 CONFIG 딕셔너리)

| 항목 | 기본값 | 설명 |
|------|--------|------|
| `jaccard_threshold_numeric` | 0.5 | DB 저장 시 같은 번호 제목 중복 판정 |
| `jaccard_threshold_text` | 0.6 | DB 저장 시 다른 번호 제목 중복 판정 |
| `_dedup_pool_by_title` threshold_numeric | 0.35 | Phase 2.5: 분析 전 동일 제품 클러스터링 |
| `_dedup_pool_by_title` threshold_text | 0.50 | Phase 2.5: 분析 전 유사 기사 클러스터링 |
| `_dedup_analyzed_by_keywords` threshold | 0.30 | Phase 3.6: 분析 후 의미적 중복 클러스터링 |

## 시간대 처리 규칙

| 상황 | 사용 시간대 | 이유 |
|------|-----------|------|
| DB 저장 (`collected_at`) | UTC | DB 저장 표준 |
| 표시·파일명·로그 | KST | 사용자 가독성 |
| 오늘 기사 집계 기준 | KST 자정 | 업무일 기준 |
| RSS 피드 날짜 비교 | UTC | RFC 2822 기준 |

KST 처리: `_KST_TZ = pytz.timezone('Asia/Seoul')` / `_now_kst()` 헬퍼 사용.
